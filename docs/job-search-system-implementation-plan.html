03 / Setup and sign-in

Run the current local version

These instructions apply to the existing implementation. The hosted release uses a public HTTPS URL, Google Web OAuth and managed storage as specified in section 9.

1. Start locally

Use Node.js 20.19+ or 22+ as recommended by this project. From the repository directory:

npm ci
npm run build
npm start

Open http://127.0.0.1:4318 in Chrome and keep the terminal running. On this Mac, Start ApplyWeave.command is also available. For development use npm run dev.

2. Configure Google once on a fresh installation

  1. Select a Google Cloud project and enable Google Sheets API. Configure OAuth consent and add your owner account as a test user if the application is External / Testing.
  2. Create a Desktop app OAuth client and download its JSON. This is the client type for the current local app.
  3. Run the local bootstrap command below with your downloaded file and private tracker ID. Do not commit credentials.
npm run configure-google -- /path/to/desktop-client.json YOUR_SPREADSHEET_ID

This computer is already configured. Sheets API is enabled and live sync has succeeded. The Google Sheet does not need public edit access; the signed-in owner must have edit access. Signing into Chrome or connecting Google Drive to Codex does not authorize ApplyWeave itself.

3. Sign in and sync

Click Sign in with Google, choose the tracker owner and complete consent. The backend verifies the Google identity, checks the approved profile email when establishing ownership, and pins the verified account ID. Other accounts cannot open this workspace. Click Sync Google Sheets and inspect the result.

The local callback is http://127.0.0.1:4318/api/auth/google/callback. Scopes are openid, email and spreadsheets. The Sheets grant covers spreadsheets accessible to the account; this app targets the configured tracker.

Session and Google grant are separateAn HttpOnly, SameSite=Lax browser session lasts up to seven days and ends when the server restarts. Sign out clears the session and private UI while retaining the Sheets grant. Disconnect Google removes the stored token. A revoked or expired grant requires reconnection.

A fresh clone has no private profile or PDFs. After sign-in, import your approved profile or restore your private workspace backup, and copy catalogued PDFs into the private resume directory.

Statuses: Saved, Preparing, Applied, Assessment, Interview, Offer, Rejected, Withdrawn. Record actual submission dates and submitted resume versions. Unknown dates remain unknown; later draft recommendations do not replace a submitted resume choice. Use Withdrawn to retain history.

Synchronization rules

  • Stable AW-... IDs connect the app, Sheet, pack and Chrome bundle. Do not edit IDs or formula cells casually.
  • Read-before-write checks detect simultaneous edits and duplicate IDs. Review conflicts and deliberately select the correct version.
  • Application changes stay visibly pending until sync succeeds. Writes use plain values so pasted job text does not become a formula.
  • Checked profile rows can be pulled from Sheets. Concurrent profile edits trigger a conflict; local profile edits require explicit reviewed export/import to publish to the Sheet.
  • Answer-pack text stays local. The Sheet alone is not a complete backup of the workspace.

Optional bound sidebar

The tracker works without this. The Apps Script source and installer are implemented, but installation/live validation are pending. Enable Apps Script API and API access in Apps Script settings, then use Authorize sidebar installation and Install Sheet sidebar in app Settings. Authorization adds script.projects; script menu actions may request current-spreadsheet and container-UI permissions.

Manual setup: open the Sheet's Extensions → Apps Script, copy apps-script/Code.gs and apps-script/Sidebar.html (HTML file named Sidebar), run setupApplyWeave and reload. Existing matching tabs are preserved; mismatched headers are refused. The editor link previously returned a Google “Page not found” error; the API installer provides another route.

05 / Application assistant

Prepare answers from approved evidence

Inputs are a saved application, pasted job description, questions and character limits, approved profile, preferences and resume catalogue. Outputs include fit/compensation/work-mode checks, unknowns, resume recommendation with reasons, referenced proof points and editable answer drafts.

Resume IDCurrent role in the catalogue
SDEOriginal general software-engineering / DSA evidence.
MERNOriginal JavaScript, MERN and full-stack evidence.
PYTHONOriginal Python/backend evidence.
STARTUPOriginal startup/product ownership evidence.
FRONTENDDerived frontend PDF; created from approved facts, candidate review before upload.
AIDerived applied-AI PDF; created from approved facts, candidate review before upload.

The current profile has 17 approved facts and six resume versions. The user confirmed source employment dates, metrics, project descriptions and contact details. This permits reuse of those facts; it does not justify inventing missing qualifications, achievements or production AI experience.

  1. Generate a draft in Prepare using the installed, signed-in Codex CLI. Run codex login if needed, or set CODEX_BIN before starting the app for a custom installation.
  2. Review job fit, unknowns and resume choice, then inspect each answer and its supporting facts. Generation uses Codex account limits; no separate API key is used by the current implementation.
  3. Edit and explicitly approve accurate answers, respecting character limits. Every generated answer begins unapproved. Editing evidence or wording invalidates approval; changed profiles invalidate old pack exports.
  4. Save the pack and export a Chrome bundle containing the approved profile plus that application's pack. Manual drafting remains available.

Generation disables shell, browser, plugins and other tools, treats job descriptions as untrusted input, and validates structured results. Version checks reject stale in-flight results after application/profile/pack edits. Sensitive declarations and judgments stay manual.

PDF downloads are limited to files in the approved catalogue under private/resumes/. To add one, copy the PDF there and add its ID and plain filename to the profile catalogue. Real job-description trials remain a user-pilot step.

06 / Chrome helper

Review first, then fill selected fields

npm --prefix extension ci
npm --prefix extension run build
  1. Open chrome://extensions yourself, enable Developer mode and choose Load unpacked → extension/dist. Automated access to that Chrome page is blocked in this environment.
  2. Pin ApplyWeave and open its persistent side panel on a company application page.
  3. Import the reviewed Chrome bundle. Enable the exact company hostname you want to use.
  4. Scan, review the proposed values, select fields, and fill. Rescan after page or profile changes.

Permissions are activeTab, scripting, storage and sidePanel; there is no blanket website host permission. Supported fields include approved contact/education details and exact matches to approved application answers, subject to type and value checks.

Manual actions remain part of the workflowThe helper never overwrites existing values or clicks Submit. LinkedIn and Wellfound are blocked for on-page interaction; use prepared copy/paste there. Salary, sponsorship, legal declarations, self-identification, CAPTCHA, file uploads and unsupported/custom controls require you. Dropdowns, iframes and shadow DOM may need manual entry.

Safe installation pilot

python3 -m http.server 4320 --bind 127.0.0.1 --directory extension

Open 127.0.0.1:4320/test-form.html in Chrome and explicitly enable that hostname. Check scan, preview, selected filling, manual-field explanations and preservation of existing values with sample data. Then pilot a chosen company portal. Build completion does not confirm Chrome installation or compatibility with every portal.

07 / Daily workflow

The happy path

Hosted target: open your deployed HTTPS URL and sign in; no local terminal is needed. The steps below already describe the feature workflow, with local startup required only until migration is complete.

  1. Start and sign in. Open ApplyWeave and review the Dashboard's next actions.
  2. Find a role. Browse LinkedIn, Wellfound or company sites yourself. Save URL, title, work mode, known compensation and job description with Add application.
  3. Prepare. Open the saved role in Prepare, enter questions/limits, generate, inspect evidence, edit and approve. Download the appropriate resume after reviewing it.
  4. Transfer. Save the pack, download Chrome bundle and import it in the side panel.
  5. Apply. On an approved company portal, scan and preview, fill selected supported fields, complete manual fields, upload the PDF and review the entire form. Submit yourself. For LinkedIn/Wellfound, copy/paste manually.
  6. Record the outcome. Mark Applied only after submission; record actual date/resume, recruiter details, next action and due date.
  7. Sync and follow up. Sync Google Sheets, resolve conflicts if any, and confirm success. Update assessment/interview/outcome stages as they happen.

The time savings come from reusing verified facts, drafting answers in one place, reducing repeated typing and keeping a single status history. Google sync is explicit; neither a local save nor filling a form proves an employer received an application.

08 / Recovery and troubleshooting

Keep your work recoverable

This section records current local recovery. The hosted release must provide equivalent JSON/PDF export, restore and provider-pause recovery through the deployment plan.

Export a workspace JSON backup from Settings before major edits or moving computers. It includes profile, preferences, applications and packs. It excludes PDF binaries, OAuth credentials/tokens and browser sessions. Back up private/resumes/ separately with catalogue filenames intact.

For recovery: install dependencies, configure Desktop OAuth and tracker ID, sign in, restore the JSON through Settings, copy PDFs back and inspect records before syncing. Restore replaces workspace contents and marks applications pending; back up the destination first. Reinstall the extension and import a fresh bundle.

Private files and credentials are Git-ignored with restricted local access; this is not an encrypted vault. Exported bundles/backups also contain personal information. Private APIs require a session and mutating requests have CSRF/origin checks. The loopback HTTP cookie intentionally differs from the Secure cookie required for a hosted HTTPS deployment.

09 / Required hosted release

Deploy using free service tiers

New delivery requirementDeliver a single-owner HTTPS application that works with this Mac switched off. Preserve all three features: Google Sheets tracking, reviewed answer generation and the separately installed Chrome helper. Use free hosting/data tiers within their allowances, with no automatic paid upgrade. This section defines the target release. The app is deployed, with cloud storage and production settings configured; authenticated workflow acceptance remains pending.

Recommended target: Vercel Hobby + Supabase Free

Keep React, TypeScript, Vite and the Express business logic. Host the web UI and API on Vercel; use Supabase Postgres for persistent data and a private Supabase Storage bucket for resumes. Continue using Google Sheets as the shared tracker. The application keeps its own Google sign-in/session flow; Supabase is the data/storage provider, so introducing a second authentication system is unnecessary.

Chrome / hosted React UI↔HTTPS Express API↔Postgres + private PDFs

The API also calls Google OAuth, Google Sheets and the selected hosted AI API. Reviewed application bundles continue to move from the web app to the Chrome side panel by explicit file import.

AI generation and cost decision

Free hosting does not supply the current Mac's Codex runtime. Full hosted generation needs a model API credential and a chosen model. Before selecting a free-quota API, check account/region availability, current limits and how it handles submitted resume/job data. Do not promise permanently free inference or transfer local Codex login files to the server.

  • Use a provider adapter so the model service can change without changing packs or approval rules.
  • Set request size, output-token, concurrency and daily-generation limits. Do not switch to a billable model automatically.
  • Keep manual drafting, editing, approval and bundle export available when the provider is unconfigured, unavailable or quota-limited.
  • Manual mode is a fallback. The full hosted release is not complete until live AI generation passes with the chosen provider. If only paid inference is suitable, obtain the user's budget decision before enabling it.

Delivery phases and exit criteria

  1. Hosting foundation. Add cloud/local adapters, migration scripts, configuration validation and a deployment entry point. Build and boot the UI/API on the free target with test data.
  2. Identity and durable data. Implement Web OAuth, owner-only access, persistent sessions, Postgres storage and private PDF upload/download. Verify data survives a cold start and redeploy.
  3. Feature parity. Connect hosted generation, Google Sheets synchronization and Chrome bundle exports. Exercise review/approval, duplicates, concurrent edits and expired grants.
  4. Isolated preview. Run the existing checks plus hosted access-control, restart, quota/error and backup/restore tests. Use an isolated tracker and sample profile.
  5. Migration and deployment. Pause local writes, export JSON/PDFs, resolve outstanding sync conflicts, import with unchanged IDs, compare counts/content, set the final callback and reauthorize. Make one controlled sync and inspect for duplicates before normal use.
  6. Real-use handover. Open the public HTTPS URL in a fresh browser while the local server is stopped. Complete save → generate → approve → export → Chrome review/fill → manual submit → status/sync. Verify resume download and a backup restore. Record the URL, limits and recovery instructions.

Rollback: retain the original private backup and PDFs, but avoid two active writers. If returning to the local app after hosted edits, first export/reconcile those edits and the Sheet, then reactivate the local workspace. Code rollbacks must remain compatible with deployed database migrations.
